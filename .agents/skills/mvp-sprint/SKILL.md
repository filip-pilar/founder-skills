# Product Scope

Define the user outcome and the uncertainty that a release should resolve. Inspect an existing implementation when available before recommending a rebuild or cuts. Choose a small complete workflow that is useful enough to test. A manual service or simple prototype may suffice; essential trust, accessibility and data-handling requirements still belong in scope.

Make explicit what to keep, defer and measure. Set completion criteria based on the actual use case. Derive the schedule from scope, dependencies and the user's deadline; do not impose a one-week deadline regardless of complexity. Distinguish estimates from commitments.

Deliver a concrete release scope and sequence, including how the first users will try it. Keep launch-channel planning in First Customers & Launch rather than reproducing its tactics. If implementation is requested, continue through the authorized build and proportionate validation; a planning-only request remains read-only.
